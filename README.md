把四个 UI 项目——**驾享租 APP 设计 / 数据可视化 / AI 衣橱 / 时愈**——做成一个可分享的网页。
设计稿原样呈现，外面套了一层真正的网页外壳：固定章节导航、滚动进度、目录卡片点击跳转、
点击放大看细节、手机端适配。

> **本仓库是「UI 全项目」版**，线上 <https://sunqian321.github.io/portfolio-ui-all/>。
> 另外四版在各自的仓库里（见下面「多版本怎么维护」），五者的素材、章节顺序、文案各自独立。

**每张图导出三档宽度（1440 / 1920 / 2880，租车那张是 1440 / 1920 / 2425），
浏览器按自己的屏幕挑一档**——手机下 1440 档（省流量、解码快），Retina 笔记本下最大档（不糊）。
配合按章节懒加载，**首屏只加载 92 KB**，滚到哪才下哪。

## 这一版和其他四版最大的不同：素材是五张宽高各不相同的 PNG

其他版本要么是「一份 PDF 一页页渲」，要么是「两张 PNG」。本版是**五张 PNG 混着用，
而且宽度不统一**，这带来两个别处没有的问题：

| 素材 | 尺寸 | 用途 |
|---|---|---|
| `目录- UI设计.png` | 3840×2160 | 目录页（当封面用） |
| `app设计/租车.png` | **2425**×32768 | 01 APP设计 |
| `可视化.png` | 3840×25402 | 02 可视化设计 |
| `智能体设计-ai衣橱.png` | 3840×12722 | 03 前半 |
| `app设计/时愈.png` | 3840×18512 | 03 后半 |

### 问题一：宽度不一样，母版宽度就得逐张算

`MASTER_W = 2880` 在本版是**上限，不是目标**：

- 3840 宽的四张 → 缩到 2880，是干净的降采样，清晰度零风险；
- **2425 宽的租车** → 保持原生**不放大**，而且它的档位是 `1440 / 1920 / 2425`，
  最大档给足 2425。要是按老规矩卡在 2880 那两档，Retina 屏就只能拿到 1920，
  白白丢掉 21% 的真实像素；反过来把 2425 插值放大到 2880 也没用——多出来的像素是
  算出来的，体积变大但不会真的变清晰。

档位是 `tier_widths_for()` 按母版宽度算出来的，不用手改。

### 问题二：五张图的截图缩放不一样，裁切线也不同

这五张都是浏览器全页截图，**顶部各有一条 macOS 浏览器窗口栏**（红黄绿点 + 地址栏），
不裁的话网页上会出现「浏览器窗口里再套一个浏览器窗口」。但五张的缩放比例不同，
裁切线也就不同——3840 宽的那四张是 **160px**，2425 宽的那张是 **101px**
（都约等于「图宽 × 0.04167」，即窗口栏占整窗高的比例）。

所以本版的 `detect_crop()` 是**逐张自动探测**的，不再像品牌版那样写死一个 `CROP_TOP`。
判据是「相邻两行的整行平均亮度跳变 > 60」：窗口栏底边那一下是 248 → 0 / 144 / 152 的陡降，
非常好认。**不能用「第一个不够亮的行」**——窗口栏内部有一条 `#EFEFED` 的分割线，
下面还有一层渐变阴影，亮度是 248 → 243 → 226 → 220 → 211 慢慢降的，
逐行阈值法会在分割线或阴影起步处就误判（实测分别误判到 70 和 35）。

跑脚本时会逐张打印探测结果和按比例算出的预期值，两个数对得上就说明探对了：

```
目录- UI设计.png
    窗口栏裁切线探测：160px（按比例预期 160px）
app设计/租车.png
    窗口栏裁切线探测：101px（按比例预期 101px）
```

裁歪了的症状很好认：页面顶部露出一条带红黄绿点的白色横条。

## 改了设计稿之后怎么更新

1. 重新导出那几张 PNG，覆盖到 `作品集/投递/单独项目/ui全项目（驾-可视化-原型（ai-app）/` 下的同名文件。
2. 重跑导出（约 25 秒，会先清空 `assets/img/` 重建）：

```bash
python3 tools/build_tiles.py
```

3. **素材换了一整套的话**（比如换成另一个方向），路径用命令行传，不用改代码：

```bash
python3 tools/build_tiles.py /path/to/另一个项目目录/
```

   目录里要能找到 `SOURCES` 表里列的那几个文件名。要是文件名也变了，
   改脚本顶部的 `SOURCES` 表：

   ```python
   # (相对路径, 输出子目录, 单页名或 None, 章节名)
   SOURCES = [
       ("目录- UI设计.png",     "ch0", "cover", None),
       ("app设计/租车.png",      "ch1", None, "01 APP设计"),
       ...
   ]
   ```

   给了单页名 = 这一张整张出一张图（封面）；`None` = 进长图序列，自动切片。

4. **目录页版式变了的话，要重新量 `.toc-hit`**（见下）。
5. **章节数变了的话**，要同步改 `index.html` 的 `<section>`、导航链接，以及 `SOURCES` 表里的子目录名。
6. 本地看过没问题，再提交推送（见下）。

### ⚠️ 目录三张卡片的点击热区，是单独量的

`index.html` 里的三个 `.toc-hit` 是盖在目录页上、按画面宽度等比定位的透明点击区。
它们**不是**图片的一部分，是 CSS 写死的百分比。扫描画面里的面板色（`#404040`）得到
三张卡的真实包围盒，外面各放约 0.3% 让手指好点：

```css
.toc-hit--1{left:33.7%;width:28.0%;top:6.5%;height:53.8%}  /* 居中 · 01 APP设计 */
.toc-hit--2{left:18.2%;width:15.5%;top:8.0%;height:65.2%}  /* 最左 · 02 可视化设计 */
.toc-hit--3{left:62.1%;width:15.7%;top:7.6%;height:65.2%}  /* 最右 · 03 AI 智能体原型 */
```

两个容易踩的点：

1. **画面里的左右顺序是「02 可视化 / 01 APP设计 / 03 AI原型」，不是按编号排的。**
   所以 `--2` 在最左、`--1` 居中。写热区时要照画面位置，不是照编号顺序。
2. **卡片 01 的下半部分被那块紫色「UI设计」标签盖住**（y 60.4%~88.2%），
   所以它的高度只到 60.3%，和视觉上看得见的卡片面板对齐——否则鼠标悬停时
   高亮框会比卡片本身长出一截。

**换了目录页就要重量一遍**，不然鼠标悬停的高亮和点击跳转的落点会偏。

### 长图的刀口落在哪，是算出来的

`build_tiles.py` 的 `snap_cuts()` 不会硬按固定高度切，而是在每刀的理想位置附近
±360px 里找**整行同色**的那一行下刀，让接缝落在物料之间的空隙里，而不是从一张
界面截图中间横穿过去。找不到纯色行时（整段都是满幅截图）退化成「颜色变化最小的那行」。

跑脚本时会逐行打印每一刀的结果，`切口落在纯色行 ✓` 就是落得漂亮：

```
→ ch1/tile-02  y   5579–8904   (3325px)  切口落在纯色行 ✓
→ ch1/tile-01  y   2631–5579   (2948px)  切口色差 191
```

色差大不代表有问题——只要相邻两张接得上就看不出接缝。验证办法是把 1920 档拼回去
和母版逐像素比，接缝附近平均差在 2/255 以内就是无感的（本版实测 0.07 ~ 2.03）。

> ⚠️ 比对时注意：每张切片的高度是分别四舍五入的，**拼回来的总高会比母版差 1px**。
> 不补这个偏移，最后一刀附近会算出一个很大的差值（实测 6.99），看着像坏了一刀，
> 其实把母版偏移 -1px 再比就降到 2.05 了。

### 想调画质或体积

改 `tools/build_tiles.py` 顶部参数后重跑：

| 参数 | 现在 | 说明 |
|---|---|---|
| `MASTER_W` | `2880` | 母版宽度**上限**。比它宽的源图缩到它；比它窄的保持原生不放大，并把原生宽度加成一档。**别往下调**——Retina 屏（1440 CSS px × 2 倍像素）要的就是 2880px |
| `TIER_WIDTHS` | `[1440,1920,2880]` | 导出档位，浏览器自己挑。加档位 = 加仓库体积，一般不用动 |
| `WEBP_QUALITY` | `80` | 这几张全是界面截图，小字极多，压低会把笔画压糊，别再往下降 |
| `TILE_H` | `3000` | 只用来决定大概切几刀，实际刀口由 `snap_cuts()` 算 |
| `CHROME_RATIO` | `0.04167` | 只在自动探测失败时用来估裁切线，正常情况下用不到 |

改完重跑，脚本会先清空 `assets/img/` 再重建，**仓库图片总量 17.3 MB**，分布：

| 档位 | 体积 | 谁在用 |
|---|---|---|
| 1440 | 3.6 MB | 手机、普通笔记本 |
| 1920 | 5.4 MB | 1080p 台式 |
| 2425 | 3.1 MB | 租车那张的 Retina 档（源图原生宽度） |
| 2880 | 5.2 MB | 另外四张的 Retina 档 ← 真正清晰的这档 |

## 为什么锚点跳转不是「平滑滚动」

整页约 5.5 万像素高，最长的一章（01 APP设计）自己就占了 2.6 万。
如果按常规写 `html { scroll-behavior: smooth }`，从目录点一次导航「联系我」会变成
横穿全页的半分钟动画，沿途还要把长图切片全部下载解码一遍。

所以 `main.js` 的 `goTo()` 按距离分流：

| 距离 | 行为 |
|---|---|
| ≤ 2 屏 | 平滑滚动（60fps 动画只要几百毫秒，观感好） |
| > 2 屏 | 直接瞬移（0.33 秒到位，沿途图片根本不触发下载） |

`prefers-reduced-motion` 的用户一律瞬移。

## 性能上的几处刻意取舍

这些改动都是为了弱显卡机器（尤其 Windows 核显），在本机强 GPU 上几乎看不出差别，
所以在弱机器上出问题前不容易发现。改之前先看一眼：

| 位置 | 做法 | 原因 |
|---|---|---|
| `.nav` | 用不透明深色底，**不用 `backdrop-filter`** | 毛玻璃滚动时每帧都要重新采样背后的画面，是滚动卡顿的常见来源 |
| `.progress` | `transform: scaleX()`，**不用 `width`** | `width` 每帧触发布局+重绘；`transform` 只走合成层 |
| `main.js` 的 `measure()` | 缓存 `offsetTop` / `scrollHeight` | 读这些属性会强制同步布局。以前放在每帧的 `update()` 里，等于每帧重新布局一次 |
| `main.js` 的懒加载 | 用 `IntersectionObserver`，不用 `loading="lazy"` | 浏览器自带的懒加载在慢网下会一次性预取 8000px，把好几 MB 在首屏就拉下来 |
| `.toc-hit` | 只有 hover 反馈，**没有无限动画** | 目录页是首屏，这里放 `infinite` 动画等于让浏览器一直有活干 |

> 顺带一提：右侧那排章节圆点（`.rail`）已按用户要求移除。

## 已知限制

- **图中的文字不能选中、不能复制、搜索引擎读不到**。因为整站是设计稿导出的图片。
  如果需要可搜可复制，得把页面改写成真正的 HTML 排版，那是另一套做法。
- **本版没有「关于我」页**。素材里没有这一页，所以没有硬造，导航里也就没有这一项。
